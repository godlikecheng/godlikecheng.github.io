# Git 提交信息规范

提交信息使用中文，并采用简洁、通用的 Conventional Commits 风格。

## 基本格式

```text
<type>(<scope>): <subject>

[body]

[footer]
```

- `type` 必填，表示变更类型。
- `scope` 可选，填写受影响的模块、功能或业务域；无法准确概括时省略。
- `subject` 必填，用一句话说明本次提交完成了什么。
- `body` 和 `footer` 可选，仅在需要补充背景、影响或关联信息时使用。

## 变更类型

- `feat`：新增功能或能力。
- `fix`：修复缺陷或异常行为。
- `refactor`：不改变外部行为的代码重构。
- `perf`：性能优化。
- `docs`：文档变更。
- `test`：新增或调整测试。
- `style`：仅调整代码格式，不改变逻辑。
- `build`：构建系统、依赖或打包配置变更。
- `ci`：持续集成或自动化流程变更。
- `chore`：其他维护性变更。
- `revert`：撤销已有提交。

## 编写要求

- 标题格式为 `<type>(<scope>): <subject>`；省略作用域时使用 `<type>: <subject>`。
- `scope` 使用简短、稳定的英文模块名或业务标识，不使用文件路径。
- `subject` 使用中文，直接描述业务结果或实际改动，避免“修改代码”“优化一下”“处理问题”等模糊表述。
- 标题保持简洁，末尾不加句号、分号或感叹号。
- 一个提交应聚焦一个主题；存在多个紧密相关的改动时，在正文中分条说明。
- 正文与标题之间空一行，重点说明变更原因、主要内容及可能影响，不重复标题。
- 存在不兼容变更时，在正文或页脚中使用 `BREAKING CHANGE: <说明>` 明确标注。
- 关联任务或缺陷时，可在页脚中使用 `Refs: #123`、`Closes: #123` 等格式。
- 只根据实际变更生成信息，不虚构需求编号、测试结果、影响范围或实现内容。
- 默认只输出提交信息本身，不添加 Markdown 代码块、解释或其他前后缀。

## 示例

```text
feat(user): 增加用户隐私设置功能
```

```text
fix(auth): 修复登录过期后未正确跳转的问题
```

```text
refactor(order): 统一订单状态转换逻辑

- 提取公共状态校验方法
- 移除重复的转换代码
```

```text
build: 升级项目依赖并调整打包配置
```
